# Учебник по проекту «Итоги торгов ETS и Каспий»

Как запустить проект, как он устроен и почему сделан именно так. Каждая функция разобрана в своём разделе —
номер раздела указан рядом с её названием. Читать удобно в порядке движения данных:
сайт → парсер (5, 6) → нормализация (7) → сохранение (8) → запуск и журнал (9) → API (11) → портал (12).

---

## 1. Как запустить

Нужен только Docker Desktop (должен быть запущен).

1. Скачать проект и перейти в папку:

   ```bash
   git clone https://github.com/Vladi2lav/taskNoAI.git
   cd taskNoAI
   ```
2. Собрать и запустить всё — базу, бэкенд, планировщик, портал:

   ```bash
   docker compose up -d --build
   ```

   При старте бэкенд сам создаёт таблицы (`flask db upgrade`) и заполняет справочник бирж (`flask seed`).
3. Загрузить историю — база сначала пустая (ETS ~10 минут, Каспий ~20 минут):

   ```bash
   docker compose exec flaskapp flask parse ets
   docker compose exec flaskapp flask parse ccx
   ```
4. Открыть портал: http://localhost:3000. Дальше данные обновляются сами каждый день в 07:00.

Полезное потом:

| Команда                                             | Что делает                                                                                            |
| ---------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------- |
| `docker compose exec flaskapp flask parse ets --limit 3` | только 3 самых свежих новых дня                                                       |
| `docker compose exec flaskapp flask parse ets --full`    | перепроверить все дни (дублей не будет)                                        |
| `docker compose up -d scheduler`                         | применить новое расписание из `compose.yml` (пересборка не нужна) |
| `docker logs flaskapp`, `docker logs scheduler`        | логи бэкенда и планировщика                                                            |
| `docker compose stop`                                    | остановить всё, данные сохранятся                                                 |

- Портал: http://localhost:3000, API: http://localhost:4000, база с компьютера: `localhost:5433`.
- **Почему 5433:** на машине есть PostgreSQL от 1С на 5432. `5433:5432` в `compose.yml` значит
  «порт 5433 на компьютере → порт 5432 в контейнере». Контейнеры ходят друг к другу по внутренней
  сети по имени сервиса (`db:5432`), проброс их не касается.
- **Образ и переменные:** код запекается в образ при `--build`. Переменные окружения из `compose.yml`
  подставляются при создании контейнера. Поменял код — нужен `--build`; поменял переменную — хватит
  `up -d`. `docker compose restart` не перечитывает `compose.yml`.

Локально без Docker — см. README, раздел «Разработка без Docker».

## 2. Как устроена система

```
 ets.kz / ccx.kz
       │  requests + BeautifulSoup (HTML), openpyxl (xlsx)
       ▼
 parsers/ets.py, parsers/ccx.py     — «как достать»: сайт → список записей общего формата
       ▼
 app/utils/normalize.py             — «как привести к одному виду»
       ▼
 app/services/trade_saver.py        — «как сохранить»: справочники, замена дня, дубли
       ▼
 parsers/run.py                     — «когда и что качать»: список дней, ошибки, журнал
       ▼
 PostgreSQL (app/models.py, migrations/)
       ▼
 app/routes.py   /api/trades, /api/status
       ▼
 frontend (React + React Router)    — таблица, фильтры, сводка, состояние данных
```

Главный принцип: **каждый слой знает только соседа.** Парсер не знает про базу, сохранение не знает
про сайт, портал не знает про парсер. Поэтому вторая биржа подключилась одной строкой (9.1),
а смена вёрстки сайта ломает только один файл.

Портал читает **только локальную базу** (ТЗ п. 3): на биржи он не ходит.

## 4. Общий формат записи

Оба парсера возвращают **список словарей с одинаковыми ключами**. Благодаря этому сохранение (8)
одно на обе биржи. Нет поля на бирже — значение `None`.

| Ключ                            | ETS                                                                           | Каспий                                                                                   |
| ----------------------------------- | ----------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------- |
| `trade_date`                      | дата из заголовка файла на сайте                   | дата запрошенного дня (сверяется с колонкой «Дата») |
| `good_name_ru` / `good_name_kz` | ячейка «казахское/русское», делится по `/` | русское; казахского нет                                                    |
| `good_code`                       | «Код товара»                                                       | нет                                                                                         |
| `tnved`                           | «Код ТН ВЭД ЕАЭС», только цифры                      | так же                                                                                    |
| `unit`                            | из названия товара                                            | из названия товара                                                             |
| `seller`, `buyer`               | наименование                                                      | наименование без БИН                                                         |
| `seller_bin`, `buyer_bin`       | отдельная колонка (с 10.2025)                                | 12 цифр в конце наименования                                             |
| `seller_broker`, `buyer_broker` | есть (с 10.2025)                                                         | есть                                                                                       |
| `deals_count`                     | кол-во сделок                                                      | кол-во сделок                                                                       |
| `price_open/close/max/min`        | есть                                                                      | есть                                                                                       |
| `price_avg`                       | средневзвешенная = цена за единицу               | так же                                                                                    |
| `amount`                          | общая сумма (с 10.2025)                                            | сумма сделки                                                                        |
| `volume`                          | **вычислено**: `amount / price_avg`                          | так же                                                                                    |
| `delivery_terms`                  | нет (базис — в названии товара)                       | «Условие поставки»                                                            |

**Смысл строки:** одна строка — не одна сделка, а сводка за день по паре «покупатель + продавец + товар».

## 5. Парсер ETS — `parsers/ets.py`

### 5.1 `fetch(url, timeout)`

Единственное место, где парсер ходит в интернет: `time.sleep(PAUSE)` → `session.get(..., timeout=...)` →
`raise_for_status()`.

- Пауза 1,5 с **перед каждым** запросом (ТЗ 4.2). Раз все запросы идут через эту функцию — забыть её нельзя.
- `timeout` — не ждать вечно, если сайт молчит.
- `raise_for_status()` — ответ 404/500 превращается в исключение, а не разбирается как нормальная страница.
- `requests.Session()` переиспользует соединение и хранит `User-Agent`.

### 5.2 `crawl(url, depth, visited)` — рекурсивный обход

На каждой странице: (1) забрать файлы, если они есть (5.3); (2) перейти во все ссылки,
**адрес которых начинается с адреса текущей страницы**, и вызвать для них `crawl` же.

- Месяцы на сайте названы как попало (`itogi-torgov-2026-may`, `itogi-torgov-fevral-2026`,
  `2025-god`) — **адреса не угадываются, а собираются со страницы.**
- Правило «начинается с адреса текущей» само отсекает `/kz/`, `/en/`, меню и ссылку на себя.
- `visited` — множество уже посещённых адресов: защита от циклов. `MAX_DEPTH` — от ухода вглубь.
- `urljoin(base, href)` превращает `/upload/...` в полный адрес.

### 5.3 `files_on_page(soup, page_url)`

Находит блоки `div.i_documents_item`, в каждом — ссылку и заголовок.

- `link['href'].lower().endswith('.xlsx')` — берём только xlsx (`endswith` = «заканчивается на»).
- Дата — регуляркой `\d{2}\.\d{2}\.\d{4}` из **заголовка**, а не из атрибута `download`:
  в мае там дата, в марте — случайное имя.
- Нет ссылки или заголовка → `raise`: значит, сменилась вёрстка.

### 5.4 `header_key(cell)` и `find_columns(rows)`

- `header_key`: `'Сатып алушының атауы/\nНаименование покупателя'` → `'наименование покупателя'`
  (схлопнуть пробелы, нижний регистр, взять часть после последнего `/`).
- `find_columns`: ищет строку, где есть «наименование товара» — это заголовки (строка в разных файлах разная).
  Затем для каждого ключа из `COLUMNS` ищет колонку, **содержащую** нужный кусок текста, и запоминает номер.
- `'средневзвеш'` без окончания — на бирже опечатка «Средневзвеш**а**нная».
- `REQUIRED` — без товара, продавца и покупателя строка бессмысленна → `raise`.
  Сумма не обязательна: в файлах до 10.2025 её нет.

### 5.5 `parse_xlsx(content, trade_date)`

- `openpyxl.load_workbook(BytesIO(content), read_only=True, data_only=True)`: `content` — **байты**
  (`response.content`, не `.text`), `BytesIO` делает из байтов «файл в памяти», `data_only` — значения,
  а не формулы.
- Вложенная функция `cell(row, key)` — значение колонки по имени ключа, `None`, если колонки нет.
- **Строка-итог** пропускается по смыслу: нет продавца и покупателя. Номер строки не используется:
  итог в разных файлах выглядит по-разному (пусто / «Итого» / «Общий оборот…»).
- Объём: `(amount / price_avg).quantize(Decimal('0.001'))` — 3 знака после запятой.

### 5.6 `fetch_day(file_url, trade_date)`

Скачать xlsx и разобрать. **0 сделок в файле → `raise`**: у ETS выложенный файл без сделок —
это ошибка, и стирать день из базы по такому файлу нельзя (см. 8.3).

## 6. Парсер Каспия — `parsers/ccx.py`

### 6.1 `get_page(params)`

Запрос к таблице с параметрами (`date_from`, `date_to`, `page`) и всегда `lang=ru`
(без него страница на казахском). Три исхода:

1. есть `table.custom-table-flexible` → список словарей, по словарю на строку;
2. таблицы нет, но есть `.empty-state` («Нет данных для отображения») → `[]`: **день подтверждённо пустой**;
3. нет ни того, ни другого → `raise`: ошибка, капча, смена вёрстки — базу не трогаем.

Значение ячейки — функция `cell_text(td)`: Каспий **обрезает длинный текст многоточием прямо в HTML**
(`…Цементный завод Семей 02124000002…` — вместе с куском БИН), а полное значение кладёт в атрибут
`title`. Поэтому сначала берётся `title`, и только если его нет — видимый текст. Урок: то, что видно
на странице, не всегда полные данные — смотри в разметку.

Колонки находятся по заголовкам `thead th`, как в 5.4: словарь `COLUMNS` «мой ключ → кусок заголовка»,
`for ... enumerate(headers)` → номер колонки. Строка превращается в словарь
`{key: cells[index] ...}` — дальше в коде `row['buyer']`, а не `cells[11]`.
Если сайт вставит новую колонку, номера пересчитаются сами; если исчезнет обязательная — громкая ошибка
вместо тихой подмены данных.

### 6.2 `pages(params)` — генератор страниц

Листает `page=1, 2, 3...` и выдаёт строки через `yield` (по странице за раз).

- **Особенность Каспия:** номер страницы за концом (`page=200`) возвращает **последнюю страницу ещё раз**,
  а не пустую. Остановка — когда страница повторила предыдущую.
- `signature = sorted(tuple(row.values()) for row in rows)` — «отпечаток» страницы. `sorted` нужен,
  потому что **порядок строк на Каспии меняется между запросами**: одинаковые строки в другом порядке
  должны дать одинаковый отпечаток.
- `raise` после цикла — страховка от вечного цикла (500 страниц без повтора = что-то сломалось).

### 6.3 `list_days()`

Все календарные дни с `CCX_HISTORY_FROM` (настройка, 13.1) по сегодня.

- Почему не «взять дни из общей выдачи»: выдача Каспия обрезана примерно на **1000 строках**,
  старые дни в неё не попадают. Перебор по календарю — по одному запросу на день — лимит обходит.
- Выходные дают `[]` (6.1) и сохраняются как загруженные с 0 записей — повторно не запрашиваются.
- `date.fromisoformat('2025-02-01')` → объект `date`; `first + timedelta(days=i)` → следующий день.
- `current_app.config` — настройки Flask; парсер работает внутри приложения, поэтому они доступны.

### 6.4 `is_deal(row)` и `to_record(row, trade_date)`

- `is_deal`: `bool(clean(seller) or clean(buyer))`. У итога «ИТОГО по дате» участники `'-'`,
  `clean('-')` → `None`, `None or None` → `None`, `bool(None)` → `False`. Без `clean` строка `'-'`
  была бы «истинной» и итог прошёл бы как сделка.
- `to_record`: строка таблицы → запись общего формата (4). БИН отделяется `split_name_bin` (7.3).

### 6.5 `fetch_day(source, trade_date)`

Все страницы одного дня (`date_from = date_to`), пропуск итога и повторов (`seen`), сверка даты:
если сайт вернул другую дату — `raise`. Это защита от **молча проигнорированного фильтра**:
без неё сделки 27.10 могли бы записаться под 23.10.

### 6.6 `row.get('x')` против `row['x']`

`row['x']` падает с `KeyError`, если ключа нет; `row.get('x')` возвращает `None`.
В словаре есть только колонки, **найденные** на сайте. Поэтому: обязательные (`row['good']`) — через `[]`,
их наличие уже проверено; необязательные (`row.get('delivery_terms')`) — через `get`.

## 7. Нормализация — `app/utils/normalize.py`

| Раздел | Функция     | Пример                                                                                                |
| ------------ | ------------------ | ----------------------------------------------------------------------------------------------------------- |
| 7.1          | `clean`          | `'  ТОО\n«Ромашка» '` → `'ТОО «Ромашка»'`; `'-'` → `None`                 |
| 7.1          | `norm_text`      | `'ТОО «Ромашка»'` → `'тоо ромашка'`                                              |
| 7.2          | `to_decimal`     | `'1 234,50'`, `'103 681 783.54'`, `9363.2` → `Decimal`; мусор → `None`                     |
| 7.2          | `to_int`         | `'7'` → `7`                                                                                            |
| 7.3          | `norm_bin`       | всё кроме цифр убрать; не 12 цифр → `None`                                       |
| 7.3          | `split_name_bin` | `'АО Майкубен-Вест 050940003769'` → `('АО Майкубен-Вест', '050940003769')` |
| 7.4          | `norm_tnved`     | `'1001 99 000 0'` → `'1001990000'`                                                                     |
| 7.5          | `detect_unit`    | `'… (207 тонн) …'` → `'т'`; `'5000 ккал/кг'` → не единица                     |
| 7.6          | `split_kz_ru`    | `'aq qant/сахар белый'` → `('сахар белый', 'aq qant')`                             |

### 7.1 Две функции для названий: `clean` и `norm_text`

- `clean` — **для показа**: как у биржи, только без лишних пробелов. Прочерки `-`, `—` → `None`.
- `norm_text` — **для сравнения и поиска**: нижний регистр, `ё → е`, без кавычек. Уродливо, но
  `ТОО «Ромашка»` и `тоо "ромашка"` становятся одинаковыми.
- В справочниках две колонки: `name` (показ) и `name_norm` (поиск). Приём: **отдельно хранить то,
  что показываем, и то, по чему ищем.**

### 7.2 Деньги — только `Decimal`

`0.1 + 0.2 = 0.30000000000000004` во `float`. Для денег — `Decimal` в коде и `NUMERIC(18,2)` в базе.

- `isinstance(value, Decimal)` — «уже Decimal? вернуть как есть».
- Убираются обычные пробелы и `'\xa0'` (неразрывный пробел — невидимый, Excel ставит его между тысячами),
  запятая → точка.
- `try / except InvalidOperation` → `None` вместо падения. Плюс: одна кривая ячейка не роняет день.
  Минус: смена формата чисел молча обнулит суммы — за количеством пустых сумм надо следить.

### 7.3 БИН

- `norm_bin` — 12 цифр или `None`.
- `split_name_bin` — регулярка `\s*(\d{12})\s*$`: `\d{12}` — 12 цифр, `$` — конец строки,
  `( )` — то, что достаётся через `match.group(1)`, `match.start()` — где совпадение началось.
  Ограничение: при 14 цифрах в конце возьмёт последние 12 — для БИН на Каспии такого не встречалось.

### 7.5 Единицы измерения

Словарь регулярок `UNITS`. `(?<!/)` — «перед словом нет `/`»: иначе в «5000 ккал/кг» уголь стал бы «кг».
Определяется не всегда — это эвристика.

## 8. Сохранение — `app/services/trade_saver.py`

### 8.1 `Lookup` — справочники «найти или создать»

Методы `good`, `participant`, `broker`. Каждый: (1) смотрит в кэш — не спрашивать базу 100 раз за файл;
(2) ищет в базе; (3) не нашёл — создаёт и делает `db.session.flush()` (отправить INSERT и получить `id`,
**не** завершая транзакцию).

- Товар: на ETS — по коду, иначе по `name_norm`. Дозаполняет пустые `name_kz`, `tnved`, `unit`.
- Участник: есть БИН — по БИН, нет — по `name_norm`.
- Брокер: по `name_norm`.
- Нечёткое объединение («похожие названия») не делается: «пшеница 3 класса» и «4 класса» почти совпадают,
  а склеенные по ошибке записи не разделить.

### 8.2 `make_hash(exchange_code, record, occurrence)` — отпечаток строки

Склеить нормализованные поля через `|` → SHA-256 → 64 символа. Одинаковые данные — всегда одинаковый отпечаток.
`occurrence` — номер повтора, если в одном файле две одинаковые строки (0, 1, ...): обе сохранятся,
и при повторной загрузке получат те же номера.
**Почему не `unique(дата, товар, продавец...)`:** в PostgreSQL `NULL ≠ NULL`, и строка без брокера
пролезла бы дважды. Отпечаток никогда не `NULL`.

### 8.3 `save_day(...)` — день заменяется целиком

В **одной транзакции**:

1. запомнить отпечатки, которые уже были за этот день (`old_hashes`);
2. `DELETE` всех сделок этой биржи за этот день;
3. `INSERT` свежих строк (`ON CONFLICT DO NOTHING` — на случай одинаковых внутри загрузки);
4. отметить день в `trading_days` (8.4) и `commit`.

Зачем: биржа может **исправить сумму** или **удалить** ошибочную сделку. Дописывание к старым данным
оставило бы ошибку навсегда или дало бы вторую запись. Если что-то упадёт посередине — `rollback`
вернёт и удалённое: момента «день пустой» не бывает.

**Когда стирать нельзя:** стирание безопасно, только если сайт **явно** подтвердил содержимое —
хотя бы одна сделка, или (Каспий) сообщение «Нет данных». Любая другая странность — ошибка в парсере
(5.6, 6.1), до `save_day` дело не доходит.

Возвращает `(добавлено, без изменений)`: сравнение отпечатков «было/стало». Удалённые биржей — в лог.

### 8.4 `mark_day(...)` и `get_exchange(code)`

- `mark_day` — найти или создать строку `trading_days` и записать статус `loaded`/`error`, число строк, время.
- `get_exchange` — биржа по коду или понятная ошибка «выполните flask seed».

## 9. Запуск и журнал — `parsers/run.py`

### 9.1 `PARSERS` и `run_parser(code, trigger, full, limit)`

```python
PARSERS = {'ets': (ets.crawl, ets.fetch_day), 'ccx': (ccx.list_days, ccx.fetch_day)}
```

Каждый парсер — пара функций: «какие дни есть» и «скачай один день». Новая биржа — одна строка.

Порядок работы:

1. Создать запись в `parser_runs` и **сразу** `commit` — упавший запуск тоже останется в журнале.
2. Получить список дней, выкинуть уже загруженные (9.2).
3. Для каждого дня — `try`: скачать, сохранить. `except`: `rollback` **только этого дня**,
   запомнить ошибку, отметить день `error`, **продолжить** со следующего.
4. В конце — статус `success`/`error`, тексты ошибок, время окончания.

**Почему `try` внутри цикла, а не вокруг:** вокруг — одна ошибка на 40-м дне остановила бы загрузку,
дни 41–300 не загрузились бы вовсе.

Параметры `date_from` и `date_to` обрезают список дней по периоду — их передаёт ручной запуск из портала (11.6).

### 9.2 `loaded_days` и перепроверка свежих дней

Загружаются дни, которых нет в `trading_days` со статусом `loaded`, **плюс последние `RECHECK_DAYS`**
(13.1) дней всегда: итоги могут появиться на бирже с опозданием. Упавшие дни (`error`) не считаются
загруженными и повторяются автоматически. `--full` — перепроверить всё; `--limit N` — только N свежих.

## 10. База данных

### 10.1 `extensions.py`

`db = SQLAlchemy()` и `migrate = Migrate()` создаются отдельно и привязываются к приложению в `create_app`
(`db.init_app(app)`). Иначе модели импортировали бы приложение, а приложение — модели: циклический импорт.

### 10.2 `models.py`

Класс = таблица, `db.Column` = колонка. `db.ForeignKey('exchanges.id')` — внешний ключ (имя **таблицы**).
`db.relationship(...)` — не колонка, а удобная ссылка: `trade.good.name_ru`.
У `Trade` два внешних ключа на `participants` (продавец, покупатель) — поэтому в `relationship`
указан `foreign_keys=[...]`, иначе SQLAlchemy не поймёт, какую колонку брать.
Индексы — по полям фильтров: дата, биржа+дата, сумма, товар, участники, брокеры.

### 10.3 Миграции

Поменял `models.py` → `flask db migrate -m "..."` (**локально**: файл создаётся там, где запущено) →
**прочитать** файл в `migrations/versions/` → `flask db upgrade`. В контейнере при старте выполняется
только `upgrade`. Автогенерация видит переименование колонки как «удалить + создать» — данные пропадут,
такое правится руками на `op.alter_column`. В проекте три миграции: исходная схема, снятие `unique`
с названия товара, увеличение длины названий до 1000.

## 11. API — `app/routes.py`

### 11.1 `trade_filters(args)` — фильтры

Каждый фильтр: поле заполнено → добавить условие в список.

- биржа: `Trade.exchange.has(Exchange.code == 'ets')` — `has` идёт по связи в другую таблицу;
- период: `Trade.trade_date >= ...`, `<= ...`; некорректная дата игнорируется (`parse_date` → `None`);
- товар: `name_norm` **содержит** текст или ТН ВЭД **начинается** с цифр;
- продавец/покупатель: 12 цифр → точно по БИН, иначе по куску названия. Подзапрос `ids`
  («id подходящих участников») и `or_(seller_id IN ids, buyer_id IN ids)`;
- брокер: так же по двум брокерам;
- сумма: `>=`, `<=`; не число → игнорируется;
- место поставки: в `delivery_terms` (Каспий) **или** в названии товара (у ETS базис в названии).
- `autoescape=True` — `%` и `_` ищутся как символы, а не как шаблоны `LIKE`.

`.where(*conditions)` — `*` раскладывает список в аргументы; несколько условий соединяются через **AND**,
поэтому фильтры работают в комбинации.

### 11.2 `summary(conditions)`

Число сделок, сумма, число товаров и разбивка по биржам — **по тому же списку условий**,
поэтому сводка всегда соответствует таблице.

### 11.3 `get_trades()`

- `page`, `per_page` (1–500), `sort` — **только из белого списка** `SORT_COLUMNS`: строку из URL нельзя
  подставлять в SQL (SQL-инъекция).
- `nulls_last()` — при `DESC` PostgreSQL ставит пустые значения первыми.
- `joinedload(...)` — подтянуть биржу, товар, участников и брокеров **одним** запросом. Без этого на
  50 строк было бы 50 × 6 отдельных запросов (проблема N+1).
- `limit/offset` — постраничный вывод.

### 11.4 `get_status()` — состояние данных (ТЗ 6.3)

По каждой бирже: записей, период, **последнее обновление** (время последней успешной загрузки дня),
загружено дней, дней с ошибкой, последний запуск. Плюс общее число записей и журнал последних
20 запусков.

### 11.5 `trades_query(args)` и `export_trades()` — выгрузка в Excel

`trades_query` строит запрос «фильтры + сортировка + подгрузка справочников» и используется **и таблицей,
и выгрузкой** — поэтому Excel всегда совпадает с тем, что на экране. Таблица добавляет `limit/offset`
(страница), выгрузка — общий предел 100 000 строк.

Файл собирается в памяти:

- `Workbook(write_only=True)` — режим «только запись»: строки пишутся потоком, не держатся все в памяти;
- `WriteOnlyCell` + `Font(bold=True)` — жирная шапка; `freeze_panes = 'A2'` — шапка не уезжает при прокрутке;
- `column_dimensions[...].width` — ширина колонок;
- `workbook.save(BytesIO())` → `send_file(..., as_attachment=True, download_name=...)` — отдать байты
  браузеру как скачиваемый файл. На диск ничего не пишется.

### 11.6 `start_parse()` и `run_in_background()` — ручной запуск

`POST /api/parse` с телом `{exchange, date_from, date_to, full}`:

1. проверки: биржа известна, начало не позже конца, начало не в будущем → иначе 400 с понятным текстом;
2. если по этой бирже уже идёт загрузка (запуск `running` моложе 3 часов) → 409;
3. `threading.Thread(target=run_in_background, ..., daemon=True).start()` и сразу ответ 202 «запущено».

**Почему поток, а не парсинг прямо в запросе:** загрузка длится минуты, а gunicorn обрывает запрос через
30 секунд. Поток работает дальше, а ход загрузки виден в журнале (`parser_runs`).
`current_app._get_current_object()` — настоящий объект приложения: `current_app` — это «указатель»,
который работает только внутри запроса, а поток живёт дольше. В потоке — `with app.app_context()` (как в 13.2).

### 11.7 `get_analytics()` — данные для графиков

Те же фильтры (11.1), четыре запроса с `GROUP BY`:

- оборот: `date_trunc('month', trade_date)` — дата → первое число месяца; группировка по месяцу и бирже;
- цены: `sum(amount) / nullif(sum(volume), 0)` — **средневзвешенная** цена за месяц (крупные сделки весят
  больше мелких); `nullif(x, 0)` → `NULL` вместо деления на ноль; плюс минимум и максимум;
- топ-10 товаров и топ-10 продавцов/покупателей: `group_by` + `order_by(sum(amount).desc())` + `limit(10)`.

## 12. Портал — `frontend/src/`

### 12.1 `main.tsx`, `App.tsx`, `Nav.tsx` — маршруты

`BrowserRouter` в `main.tsx` включает роутер. В `App.tsx` **все маршруты в одном месте**:
`/` → сделки, `/status` → состояние, `*` → «не найдено». `NavLink` в меню сам подсвечивает активную страницу.

### 12.2 `api/trades.ts`

Типы данных API и функции `getTrades`, `getStatus`. `URLSearchParams` сам кодирует кириллицу;
пустые фильтры в URL не попадают.

### 12.3 `FiltersPanel.tsx` — форма

- `draft` — **черновик**: что сейчас введено в поля; при вводе запросов нет.
- `e.preventDefault()` — у HTML-формы отправка по умолчанию **перезагружает страницу**; эта строка
  отменяет её («без перезагрузки», ТЗ 6.2).
- «Применить» → `onApply(draft)`; «Сбросить» → пустые фильтры.

### 12.4 `Trades.tsx` — страница сделок

- Всё состояние запроса в одном объекте `query`: фильтры, страница, сортировка, записей на странице.
- `useEffect(() => { getTrades(query)... }, [query])` — **любое изменение `query` само делает запрос**.
  Без `[query]` эффект выполнялся бы после каждой перерисовки → бесконечный цикл запросов.
- `applyFilters`: `{ ...q, ...filters, page: 1 }` — при новом фильтре вернуться на 1-ю страницу.
- `sortBy`: та же колонка и сейчас `desc` → `asc`, иначе `desc`.

### 12.5 `Pager.tsx`

`‹ 1 … 4 5 [6] 7 8 … 20 ›`: первая, последняя и по две соседних с текущей, между ними `…`.

### 12.6 `Status.tsx` — состояние данных

Таблица по биржам (данные из 11.4: записей, период, последнее обновление, загружено дней, дней с ошибкой,
последний запуск) со строкой «Всего» и журнал последних 20 запусков. Длинный список ошибок свёрнут
в `<details>` — раскрывается по клику.

### 12.7 Как фронт достаёт API

В разработке (`npm run dev`) Vite проксирует `/api` на `localhost:4000` (`vite.config.ts`).
В Docker nginx отдаёт собранный фронт и проксирует `/api/` на `flaskapp:4000` (`nginx.conf`).

### 12.8 `ParseDialog.tsx` — окно запуска

Модальное окно: тёмный фон на весь экран (`.modal-backdrop`, `position: fixed`) и форма поверх.

- Клик по фону закрывает окно, а `e.stopPropagation()` на форме не даёт клику внутри «долететь» до фона.
- Поля: биржа, дата начала (по умолчанию неделя назад), дата окончания (сегодня), «перезагрузить
  уже загруженные». У дат `max`/`min` друг на друга — браузер не даст выбрать конец раньше начала.
- `daysAgo` собирает дату из **локальных** год/месяц/день. `toISOString()` дал бы дату по UTC — ночью
  по Алматы (UTC+5) это ещё «вчера».
- Ошибка от API (409 «уже идёт загрузка», 400) показывается в окне, оно не закрывается.

### 12.9 `Analytics.tsx` — графики (Recharts)

Графики описываются компонентами: `<ResponsiveContainer>` (подстраивается под ширину) → `<BarChart data=...>`
или `<LineChart>` → оси `<XAxis dataKey="month">`, `<YAxis>`, `<Tooltip>`, `<Legend>`, `<Bar dataKey="ETS">`,
`<Line dataKey="avg">`. `data` — массив объектов, `dataKey` — какое поле рисовать.

- Оборот — столбцы ETS и Каспий одной стопкой (`stackId`), подписи осей в виде «12,1 млрд»
  (`Intl.NumberFormat` с `notation: 'compact'`).
- Цена — линии «средняя», «минимум», «максимум». Осмысленна для одного товара — выбирается фильтром.
- Топы — таблицы с полосой-шкалой (`ShareBar`: ширина = значение / максимум × 100%):
  длинные названия товаров в подписи графика не помещаются.
- Фильтры — тот же `FiltersPanel` (12.3); `useEffect(..., [filters])` перезапрашивает данные.

### 12.10 Экспорт в Trades.tsx и обновление в Status.tsx

- «Скачать Excel» — обычная ссылка `<a href={exportUrl(query)} download>`: адрес собран из тех же
  фильтров и сортировки, что и таблица; браузер сам скачивает файл.
- `Status.tsx`: `useCallback(load)` — функция загрузки, которую можно передавать дальше без пересоздания.
  Пока в журнале есть запуск `running`, `setInterval(load, 5000)` обновляет страницу каждые 5 секунд;
  загрузка закончилась → `clearInterval` в функции очистки `useEffect`. Кнопка запуска при этом заблокирована.

  запуск загрузит все пропущенные дни.

## 14. Docker

- `flask.dockerfile`: сначала `COPY requirements.txt` + `pip install`, потом `COPY . .` — зависимости
  кэшируются и не переустанавливаются при каждой правке кода. `COPY --chown` — права сразу при копировании.
  Пользователь без прав root; `--home` — иначе gunicorn ругается на `/nonexistent`.
- `CMD`: `flask db upgrade && flask seed && exec gunicorn ...` — миграции и справочник **один раз до
  старта воркеров**. Раньше 4 воркера одновременно создавали таблицы и падали с `UniqueViolation`.
- `.dockerignore`: `.venv`, `**/__pycache__`. Без него в образ уходил venv (72 МБ). В `.dockerignore`
  без `**/` шаблон действует только в корне.
- `frontend.dockerfile`: сборка Vite в Node, результат — в nginx (`nginx.conf`, `try_files ... /index.html`,
  чтобы маршруты React открывались по прямой ссылке).
